## Objective and already-decided CLI contracts

Finish **one bounded Step 1.5d**: integrate `-L` (launch **one** managed window from a single recipe passed as *separate positional arguments*) and `-l` (a human-readable managed-window listing), then perform proportionate integrated regression on native X11 and Wayland. Do **not** ask the maintainer to choose between unrelated `-L` syntax proposals: the original architecture already specifies:

```text
joetoo-kwin [-v|-q ...] -L DESKTOP PROGRAM MODE TARGET [LAYER]
joetoo-kwin [-v|-q ...] -l
```

This is the same logical **`DESKTOP|PROGRAM|MODE|TARGET[|LAYER]`** recipe accepted by `-o`, with the existing field order, accepted program/mode combinations and validators. **Exception by maintainer decision:** omission of LAYER in *single-window* `-L` means `over`; omission in existing multi-recipe `-o` remains the accepted implicit `panel` default. Do not silently change `-o` or reinterpret a blank fifth field for existing plans. `-L` receives individual shell arguments, **not** one pipe-delimited string and not arbitrary geometry/program argv. For example (illustrative, not a guaranteed reachable host): `joetoo-kwin -L 3 sdl-freerdp rdp rdp://joe@host.example:3389 panel`. Slot is not a sixth argument: derive/reserve it using the established managed-slot and shared launch rules. The `LAYER` choice now also governs the relationship of the new window to **currently managed windows** on the same desktop, not just windows in a newly launched one-entry cohort. Respect existing `-f`/configuration-layer behavior where it can be reused without silent precedence changes; explicitly document the effective layout/defaults.

## Maintainer-approved incremental layout behavior for `-L` (2026-11-11)

This is an **extension of the existing shared managed-layout policy to a live desktop**, not permission to move unrelated or merely observed KWin windows. The existing `-o` default for omitted LAYER is **`panel`**; **only `-L` defaults omitted LAYER to `over`** so the new window is conspicuous. Respect the established interpretation of `under`, `panel`, `over` as **one-shot** initial layout/stacking classifications, not permanent always-on-top/bottom rules.

- **`over` or `under`:** use the existing configurable graphical region and per-desktop cascade policy, accounting for the **already managed, currently present** windows of the corresponding layer. The new window participates in the existing under → panel → over stack order and relevant same-layer order. Do not treat a single-entry `-L` as a fresh desktop with no peers; do not recascade windows on *other* desktops or change unrelated/unmanaged windows. Prefer to leave existing managed peer geometry intact where possible; if same-layer cascade adjustments are necessary, use exact managed identity and verified geometry/stacking with a bounded, safe transaction. Do not create a continuously enforced Z-order rule.
- **Explicit `panel`:** the ordinary four-panel physical allocator remains an absolute limit. Count existing paneled positions/managed reservations on the intended desktop **plus** the new panel using the authoritative registry and any approved layout metadata. If the projected count **exceeds four**, reject at preflight with a clear error (desktop, existing panel count, maximum four), **before launching the child or moving anything**. If projected count is **1–4**, compute the **entire new panel geometry as a group** using the existing one-/two-/three-/four-panel layout algorithm. Then **reflow the other currently present, positively managed panel windows and place the newly launched panel window** so all fit. A new panel must not merely be placed into a pre-existing single panel's rectangle. Preserve the original `MANAGED_ID`, `WINDOW_UUID`, intended desktop/slot and ownership of every existing panel; geometry adjustments do **not** reassign logical slots. Missing/reserved managed entries must not be treated as free slots or silently discarded.
- **Safety and reconciliation:** the currently accepted broker `ListManaged` record is known to expose intended desktop/slot, UUID, presence and placement, but the *availability of persistent layer membership and ordering for already managed windows has not been established*. Inspect the actual broker/resident/client contracts before assuming it can reconstruct `panel` vs `under` vs `over`. Determine the smallest truthful way to retain/query necessary per-window layer and ordering state within Step 1.5d, without speculative persistence/restart adoption (Step 1.7) or guessing by window geometry/title. Any extension must preserve existing methods, exact UUID ownership, missing-slot reservations and proven `-o` behavior. If the live layout cannot be reconstructed unambiguously, fail closed with a helpful diagnostic rather than moving unidentified windows.
- **Transaction ordering and partial failures:** perform all validation, inventory/slot/capacity checks, and geometry planning **before confirmation** and before any window motion or child spawn. Recheck mutable broker state immediately before applying an authorized layout; never depend on a stale inventory or force past Busy. Distinguish the full intended resulting desktop arrangement from a one-window launch plan in the confirmation display, including when existing windows will be moved. Prevent an arbitrary partial reflow: choose and document a bounded owner/UUID-verified update order and clear handling of launcher failure, placement failure, mid-transaction process loss and incomplete geometry verification, preserving existing windows where safe. Do not claim atomicity or perfect rollback if unsupported by the current KWin/bridge APIs. If the necessary change to shared broker/resident transactions is materially larger than a bounded Step 1.5d adjustment, surface the exact limitation and smallest implementation option rather than silently broadening APIs.
- **Logical slot vs panel index:** logical slot remains a managed identity/reservation coordinate, independent of layer or the 1–4 panel position. Do not count all logical slots as panels, and do not renumber previously managed windows. Check how `-o` derives and reserves slots, and choose a collision-free logical slot for `-L` that preserves historical missing reservations; if a safe choice cannot be identified, return an explicit preflight error.

Existing architecture describes four-panel limits, shared panel geometry, cascade and stacking. The new live-desktop behavior should **reuse** those policies rather than reimplementing inconsistent geometry. The requested behavior is intentional; avoid replacing it with a “launch only, no reflow” shortcut simply because that would be easier.

**Required operator-oriented validation for `-L`:** Validate **all** fields with the same existing recipe parser and program/mode/target validators that `-o` uses, before confirmation or network/process side effects. Reject wrong operand count, invalid desktop, unsupported PROGRAM, invalid MODE for that PROGRAM, malformed/unsafe TARGET, invalid LAYER, and duplicate/reserved slot or broker/preflight failure. Explain **which field/requirement** failed and what value or pattern is expected, in a clear, concise error message; do not collapse ordinary `-L` recipe errors into an unhelpful generic `Invalid RDP target/settings`. For sensitive targets, do **not** echo full arbitrary input or credentials: report a redacted offending field and safe expected syntax when necessary. Preserve existing `-o` fail-closed validation, without relaxing any security or introducing a second parallel parser. The normal launch still shows the one-entry effective plan and requests confirmation before side effects, following established safety and Ctrl-C/negative-answer conventions. Preserve truthful incomplete/failure results and owner/source/UUID invariants.

**Required `-l` presentation:** A **read-only table of managed windows**, **one row per broker-managed record**, in aligned **fixed-width columns** readable in a terminal. The operator must be able to identify **other managed windows** before later commands (e.g. future `-d MANAGED_ID`); `-l` does not delete, activate, enroll, move or adopt any window. Use the authoritative read-only `ListManaged` result, cross-check its schema and existing `GetManaged`/registry semantics; never infer management from unrelated KDE windows. At minimum make the stable `MANAGED_ID`, `DESKTOP`, `SLOT`, `PRESENCE`, `PLACEMENT` and full `WINDOW_UUID` available in distinct columns. If trustworthy broker fields for title/type/target or connection state are present and safe to display, select useful additions without fabricating them. Do not label `connection=not_attempted` as “disconnected” or claim remote TLS/authentication from a successful local placement. Include **missing** records, since their retained desktop/slot reservations matter; clearly distinguish them from present records. Make the output deterministic (prefer desktop, then slot, then managed ID), print a clear empty-state message for an empty registry, and distinguish broker unavailable/malformed/inconsistent responses with nonzero exit rather than presenting an empty success. Fixed-width column formatting should not silently truncate the unique identifier required for future `-d`; use sensible width/overflow handling for unusually long optional content. Do not expose credentials or private log paths. Leave `-i` and `-s` for their separately planned future interfaces.
